2. 背景与目标
2.1 背景
项目任务、系统需求、软件需求和测试执行信息分散在 ALM、DOORS 与 QC 中。用户需要分别打开多个系统才能判断当前项目有哪些工作项、需求是否完成、测试是否通过，以及 DOORS 需求是否已形成完整的 ALM 和 QC 追踪链路。

原始系统中的字段、状态和标识方式不同，且数据规模较大。若只展示静态示例数据或未经验证的模糊关联，会导致项目判断与真实数据不一致。

2.2 产品目标
Task Page 应提供一个统一工作台，使用户能够：

通过 ALMRTCrequest 登录 RTC，并按 Project Area、Timeline、完整 Iteration 路径配置和获取 ALM 数据。
主动选择 Jenkins Project，从其最新成功 Build 拉取 DOORS/QC 导出，不创建新 Build。
在需要生成新导出数据时，经用户确认后触发并跟踪一次 Jenkins Build；Build 成功后不自动 Pull。
将三个来源的数据规范化为统一任务模型。
通过表格和看板查看任务状态、负责人、到期时间及原始状态。
使用导出系统中的精确标识重建 DOORS→ALM、DOORS→QC 追踪关系。
按 Jenkins Project、已加载数据的 Iteration/Baseline、任务属性和 Trace category 筛选。
在长时间构建和拉取过程中看到进度、阶段、日志和逐来源状态。
2.3 成功定义
本期完成的最低标准是：测试人员可以从空页面开始配置并获取 ALM 数据、从最新成功 Jenkins Build 获取 DOORS/QC 数据，并在获授权的测试 Job 上完成一次 Trigger Build；三种操作互不隐式触发。

3. 用户与使用场景
3.1 目标用户
用户角色	主要诉求
PCM	查看项目工作量、未完成项、质量问题和端到端覆盖情况
数据维护/支持人员	通过 Pull 日志定位 Jenkins、RTC、文件或配置问题
3.2 核心场景
用户首次进入 Task Page，页面不自动访问 Task 后端，也不展示历史任务。
用户展开 Project 下拉框，系统从 Jenkins 获取当前 job 列表。
用户通过 ALMRTCrequest 登录 RTC，选择 Timeline 和完整 Iteration Scope，再明确点击获取 ALM 数据。
用户选择 Jenkins Project 后点击 Pull Jenkins (QC / DOORS)，读取已有的最新成功 Build。
用户需要生成新数据时，点击 Trigger Build，确认 Project 后仅等待本次 Queue ID 对应的 Build 完成。
操作完成后，用户在 Table、Kanban、Traceability 三种视图之间切换。
用户按 Jenkins Project、已加载数据的 Iteration/Baseline、关键字、Type、Source、Status 或 Trace category 缩小结果范围。
用户展开一条 Traceability 记录，检查 DOORS、ALM、QC 的具体节点及链接依据。
某一数据源不可用时，用户根据页面错误和进度日志判断失败原因，同时保留操作前已展示的数据。
4. 范围
4.1 本期范围内
Jenkins Project 列表读取。
用户通过独立操作主动触发 ALM 或 DOORS/QC 数据拉取。
经用户确认后触发新的 Jenkins Build；成功后不自动 Pull。
拉取进度、阶段、实时日志和结果提示。
ALM、DOORS、QC 统一任务模型与状态标准化。
Task Summary 统计。
Task Table。
Kanban Board。
Traceability Matrix 与详情展开。
Jenkins Project、已加载 Iteration/Baseline、关键字、类型、来源、状态和追踪分类筛选。
分页及每页 25/50/100 条切换。
基于精确导出标识的跨来源链接重建。
数据源缺失、权限失败、并发 Pull 等异常提示。
4.2 本期范围外
页面打开时自动触发 Jenkins Build 或自动 Pull。
未经用户确认触发 Jenkins Build。
同时触发多个 Jenkins Project Build。
修改 ALM、DOORS、QC 原始记录。
Pull/Build 历史持久化（运行中操作取消属于本期范围）。
5. 总体业务流程
用户打开 Task Page
  └─ 不请求 Task 数据，页面为空

用户展开 Project
  └─ SWPM 内置 Jenkins 客户端调用 get_all_projects()
       └─ Jenkins /api/json 返回 job 名称

用户点击 ALMRTCrequest → Get ALM data from RTC
  ├─ 使用已保存的 Project Area + Timeline + 完整 Iteration 路径 Scope
  ├─ 通过 RTC 刷新所选 Scope，并解析 ALM 数据
  └─ 将 ALM 结果返回当前浏览器内存

用户点击 Pull Jenkins (QC / DOORS)
  ├─ 查询所选 job 的 lastSuccessfulBuild
  ├─ 复用或下载该 Build 的 *_ref.zip，并解压 CSV
  └─ 解析 DOORS/QC 数据并返回当前浏览器内存

用户点击 Trigger Build
  ├─ 明确确认当前 Jenkins Project
  ├─ 调用 buildWithParameters 并记录 Jenkins Queue ID
  ├─ 通过该 Queue ID 定位本次 Build 编号并轮询状态
  └─ 报告结果；成功后不执行 Pull

FR-INIT-004	P0	页面工具栏应提供 ALMRTCrequest、Pull Jenkins (QC / DOORS) 和 Trigger Build 三个职责明确的入口。	三个按钮清晰可见，互不隐式触发。
FR-INIT-005	P1	Pull 失败时，不得清空当前页面已有的成功数据。	先成功 Pull，再制造失败；失败后原任务仍可查看。

FR-PROJ-004	P1	当用户尚未选择 Project 且 SWPM 本地配置中的 last_project 仍存在于 Jenkins job 列表时，系统应恢复该 Project。（记住你上一次选择了哪个 Project，下次打开下拉框时自动帮你选回来。）	首次加载项目列表后自动选择有效 last_project。
FR-PROJ-005	P0	用户更换 Jenkins Project 时，已加载数据的 Iteration/Baseline 查看筛选应被清空。	Project change 后查看筛选回到 All Iterations / Baselines。
FR-PROJ-006	P0	Jenkins 返回的 Project 即使不存在于 SWPM 本地 selection_states，普通 Pull 也不得仅因缺少选择配置而被拒绝。	未配置 Project 可进入 Pull：DOORS/QC 使用 Artifact 自动发现规则；ALM 无 scope 时明确标记为 skipped。
6.3 主动 Pull
ID	优先级	需求	可验证结果
FR-PULL-001	P0	DOORS/QC 读取只有在用户点击 Pull Jenkins (QC / DOORS) 后才启动；它与 ALM 和 Build 流程相互独立。	点击后仅发送 POST /api/tasks/pull?project=...。
FR-PULL-002	P0	Jenkins Pull 只接受明确选择的 Jenkins Project，不接受 Iteration/Scope 参数。	Project 为空返回 HTTP 400；接口无 Iteration 参数。
FR-PULL-003	P0	Pull Jenkins (QC / DOORS) 不得调用 Jenkins trigger_build() 或 RTC；只有独立的 Build/ALM 操作可访问对应来源。	网络记录中无 Jenkins Build 触发请求或 RTC 请求。
FR-PULL-004	P0	系统应查询所选 Project 的 lastSuccessfulBuild。	日志包含“Reading the latest successful data version”及 Build 编号。
FR-PULL-005	P0	系统应按第 7.1 节缓存规则获得 Jenkins Artifact 和 ALM 数据。	日志明确出现远端或缓存路径，且行为与缓存状态一致。
FR-PULL-006	P0	Pull 应作为后台任务执行，启动接口立即返回 job ID，前端轮询任务状态。	POST 返回 HTTP 202、status=running 和 job ID；页面持续更新。
FR-PULL-007	P0	同一后端实例同一时间只允许一个 Pull 或 Build & Pull 操作。	第二个并发请求返回 HTTP 409 和明确提示。
FR-PULL-008	P0	Pull 成功后，应一次性替换当前浏览器中的 Tasks、Traceability 和 Meta。	页面统计、三种视图和更新时间同时更新。
FR-PULL-009	P1	完成结果被前端消费后，后端应移除该 Pull job 结果。	使用 consume=true 获取终态后，再次查询返回 404。
FR-PULL-010	P0	普通 Pull 运行期间，用户点击 Cancel & Close 应终止本次本地 worker 并关闭进度窗口；普通 Pull 不涉及 Jenkins queue item 取消。	job 进入 Cancelled，当前页面已有成功数据保持不变，Jenkins 不收到 queue cancellation 请求。

ID	优先级	需求	可验证结果
FR-BLD-001	P0	页面应提供与 Pull 明确区分的 Trigger Build 按钮。	按钮文字和行为不同。
FR-BLD-002	P0	Build 操作必须要求用户明确选择 Jenkins Project，不得以空值触发。Project 为空时点击按钮只加载 Jenkins Project 并恢复有效 last_project，用户必须再次点击确认。	首次点击不触发 Build；直接以空 Project 调用接口返回 HTTP 400。

FR-BLD-004	P0	SWPM 内置后端应先调用 get_last_build_info(project) 记录旧编号，再调用 trigger_build(project)，即 POST Jenkins buildWithParameters。	测试桩验证调用顺序、Project 和调用次数均正确。
FR-BLD-005	P0	触发后必须保存 Queue ID，通过 queue item 的 executable 确认本次 Build 编号，再轮询该 Build。	日志和结果同时包含 Queue ID 与 Build 编号。

FR-BLD-009	P0	Trigger Build 应使用与 Pull 相同的后台 job、进度窗口、日志、并发锁和结果消费机制。	启动返回 HTTP 202/job ID；运行中第二个操作返回 409。
FR-BLD-010	P0	Trigger Build 仍在运行时，用户关闭进度窗口应取消本地 worker；若本次 queue item 尚未启动，则校验 Project 后取消该 item。已开始执行的 Jenkins Build 不得被自动终止。	运行态按钮显示 Cancel & Close；若已有 executable，结果明确说明 Build 未停止。

FR-TRC-007	P0	End-to-end coverage = round(End-to-end / All trace links × 100%)；分母为 0 时结果为 0%。	使用已知数据验证计算结果。

FR-TRC-009	P1	若没有任何精确导出链接，应显示“No exact exported cross-source links are available.”	没有 Trace 记录时显示空状态。
7. 数据来源与业务规则
7.1 数据新鲜度与缓存规则
Pull 是“基于最新成功 Jenkins Build 的缓存感知拉取”，不是“每次强制从所有远端重新下载”。必须按以下规则解释数据来源：

数据	规则	远端证据	缓存证据
Project 列表	用户首次展开 Project 时调用 Jenkins /api/json	Project 接口成功返回 jobs	本页面不保存 Project 快照
Jenkins Build 信息	每次 Pull 查询 lastSuccessfulBuild	日志含最新成功 Build 编号	不适用
Trigger Build	明确调用 buildWithParameters 并通过 Queue ID 跟踪本次 Build；SUCCESS 后结束	Queue item #q、Build #n completed successfully	不允许用旧 Build 冒充本次触发结果；不自动 Pull
DOORS/QC Artifact	若 {project}_{build}_ref.zip 已存在则复用，否则从该 Build 下载 _ref.zip	Downloading ..._ref.zip	Using local export ...
ALM scopes	仅由 ALMRTCrequest 使用保存的完整 Scope 明确请求；Scope 由 Project Area、Timeline 和完整 Iteration 路径组成	Pulling scope n/m	只有明确允许缓存的流程才显示 Using cached scope n/m
SWPM 结果	后端读取准备好的 ALM/DOORS/QC 数据，在内存中重建 Tasks 与 Traceability	Loaded n tasks and rebuilt traceability	不写 combined/derived SWPM snapshot
生成新 Jenkins 导出时先使用 Trigger Build；Build 成功后由用户明确点击 Pull Jenkins。ALM 则通过 ALMRTCrequest 独立获取。

7.5 来源解析和质量规则
ALM
ID 自动补充 ALM- 前缀。
Epic 标准化为 EPIC；包含 Story 的类型标准化为 Story；Task/Work Task 标准化为 Task；其他类型保留真实类型。
Priority 根据 Severity 映射：Critical/Blocker/High/Major/Urgent→High，Low/Minor/Trivial→Low，其他→Medium。
页面不为 ALM 人工推导 issueReason。
DOORS
已配置 Project 只装载配置中选中的 module 和 baseline；未配置 Project 自动发现本次 Artifact 中的全部 module 和 baseline。
10_AS 类型显示为 Requirement；40_Gen_SWXS 显示为 SW Requirement。
10_AS 质量问题包括：分析未完成、Rejected 未获得客户同意、Change Required 缺失、FNID 缺失、Baseline 缺失。
40_Gen_SWXS 在 Accepted/Validated 时检查：Test Status 是否 Passed、Review Status 是否 OK、是否精确链接 Story。
有任一问题时 Priority=High，否则 Medium。
QC
已配置 Project 的 Test Instance 只装载 folder path 匹配 qc_paths 的记录；未配置 Project 自动发现本次 Artifact 中的全部 QC folder path。
QC Requirement 只装载与已选 Test Instance baseline 匹配且 Requirement_Type=105 的记录。
QC Requirement 与 Test 的关系来自 QC_Req2Test.csv。
Test Instance 的执行状态不是 Passed 且 RB_Comment 为空时产生 issueReason。
QC Requirement 的 Direct Cover Status 不是 Passed 时产生 issueReason。
有 issueReason 时 Priority=High，否则 Medium。
7.6 精确 Traceability 规则
链接	精确字段/文件	说明
DOORS→ALM	DOORS external CSV 的 WorkItemID；缺失时可从 Target_URL 末尾提取数字 ID	标准化为 ALM-* 后与已加载 ALM ID 精确比较
QC Test Instance→DOORS	RB_DoorsLinks	分号拆分，按 Project+DOORS ID 优先匹配
QC Requirement→DOORS	RB_Doors_Identifier	精确匹配 DOORS Object Identifier
QC Requirement→QC Test	QC_Req2Test.csv 的 REQ_ID + TEST_ID	仅链接已选范围内 Test Instance
当同一 DOORS ID 在多个 Project 中出现时，优先按 Project+ID 匹配；只有全局候选唯一时才允许跨 Project key 回退。ALM 同 ID 多候选时优先选择 Project 相同的记录，否则使用第一个候选。

7.7 Trace category 定义
Category	判定条件	Link State
End-to-end	DOORS 同时存在已加载 ALM 节点和至少一个 QC Requirement/Test 节点	End-to-end；QC 有 issue 时为 warning，否则为 clear/ok
DOORS→ALM only	存在已加载 ALM 节点，不存在 QC 节点	Partial
DOORS→QC only	存在 QC 节点，不存在已加载 ALM 节点；即使同时有 unresolved ALM ID，仍归此类	Partial
Unresolved ALM only	不存在已加载 ALM 和 QC 节点，但 DOORS export 包含未解析 ALM ID	Unresolved
只有形成至少一条精确链接或包含 unresolved ALM reference 的 DOORS Requirement 才进入 Traceability Matrix；没有任何链接信息的 DOORS Requirement 不进入 Matrix 分母。

8. 异常和边界情况
ID	场景	系统响应	验收要求
EX-001	Jenkins Project 列表不可用	Project 接口返回错误，页面显示可读信息	不得伪造 Project 列表，不得导致页面崩溃
EX-002	未选择 Project 且没有有效 last_project	Pull 失败并提示选择 Project	不得默认选择任意 Jenkins job
EX-003	Project 不在 SWPM 本地 selection_states 中	Pull 继续执行；DOORS/QC 从该 Project 的 Jenkins Artifact 自动发现范围，ALM 标记为 skipped 并说明没有本地 scope	不得套用其他 Project 的 modules、paths 或 ALM scopes
EX-004	已有 Pull 正在运行	新请求返回 409	已运行 Pull 不受影响
EX-005	Jenkins 没有 latest successful build 或 _ref.zip	DOORS/QC 阶段记录错误	错误必须包含来源和原因
EX-006	Artifact 中缺少 DOORS module 或 QC 文件	对应来源在 meta 中记录 missing/parse error；只有来源加载器整体失败时显示 source unavailable	其他可用来源继续；缺文件的专用 UI 提示列为 DEC-004 的同类待完善项
EX-007	RTC credential 缺失或 AUTH_FAILED	ALM 阶段失败并显示登录错误	不得把认证失败显示为成功远端拉取
EX-008	某个 ALM scope 拉取失败	日志标记失败 scope；其他 scope 继续	至少一个 scope 成功时 ALM source result 返回 scopeErrors；失败详情可由日志和结果 metadata 定位
EX-009	所有远端来源均失败	Pull job 为 Failed	当前页面旧数据保持不变
EX-010	部分远端来源失败但本地仍有可解析数据	页面可以返回 partial result，但必须展示对应 pull.errors	用户能够区分最新远端成功数据和本地可用数据
EX-011	筛选结果为 0	显示视图级空状态，筛选控件保留	用户无需刷新即可取消筛选
EX-012	Trace category 结果为 0	显示 Traceability 空状态	顶部动态统计仍显示当前范围数据
EX-013	任务数超过来源最大解析数量	按配置上限截断并在 meta 标记 truncated	不得无提示地假设数据完整；UI 显式提示属于 P1 待完善项
EX-014	Pull 超过 SWPM_PULL_TIMEOUT_SECONDS	终止 worker，job 进入 Failed	错误包含 timeout 秒数
EX-015	Build 请求被 Jenkins 拒绝	Build job 进入 Failed	错误明确包含 Trigger build failed；不得继续 Pull
EX-016	新 Build 状态为 FAILURE、ABORTED 等终态	Build job 进入 Failed	显示新 Build 编号和真实终态；页面旧数据保留
EX-017	在 Build timeout 内未出现新编号或未完成	Build job 进入 Failed	区分“没有新 Build”和“新 Build 未完成”；不得回退成成功 Pull
EX-018	用户对运行中的普通 Pull 或 Build & Pull 点击 Cancel & Close	两种操作均终止本地 worker；仅 Build & Pull 存在本次 Jenkins queue item 时，校验 Project 后取消该 queue item	普通 Pull 不发送 Jenkins queue cancellation；不取消其他 Project/操作的队列项；不停止已经运行的 Build；取消失败时窗口保留并显示错误

10. 验收标准
以下用例全部通过，且无 P0 缺陷时，Task Page V1.2 才可验收。

AC-01 初始页面无后端动作
Given 用户新开或刷新 Task Page
Then 页面任务为空并显示 Pull 引导
And 不调用 Project、Pull 或 Pull status API
And 页面没有 Refresh 按钮
AC-02 Jenkins Project 来源
Given Jenkins 返回 N 个 jobs，SWPM 本地配置有有效 last_project
When 用户首次展开 Project
Then 下拉框包含这 N 个 job 名称
And 自动恢复有效 last_project
And 这些选项不依赖当前 Tasks 内容
And 已加载 Tasks 中仅作为业务展示值存在的 Project/别名不得被追加为可触发 Pull/Build 的 Jenkins job 选项
AC-03 远端完整 Pull
Given 所选 Project 已配置 scopes/modules/paths，且本地 Artifact 和 ALM cache 被安全移走
When 用户点击 Pull
Then 日志包含 Jenkins Downloading、RTC session success，以及所选 Project 实际配置数量的 Pulling scope n/m
And 日志不包含 Using local export 或 Using cached scope
And Pull 成功后 Tasks 和 Traceability 可查看
AC-04 缓存感知 Pull
Given latest successful Build 未变化，Artifact 和全部 scope cache 均存在
When 再次点击 Pull
Then 日志包含 Using local export 和 Using cached scope
And 不触发 Jenkins Build
And 最终结果仍重新解析并重建 Traceability
AC-05 Table 字段和筛选
Given 已成功加载多来源数据
When 切换到 Table 并组合 Type、Source、Status 筛选
Then 只有同时满足条件的任务显示
And 三个筛选器始终保留，即使结果为 0
And 表格最后一列是 Raw Status，不是 Quality 百分比
AC-06 Kanban 状态一致性
Given 与 AC-05 相同筛选条件
When 切换到 Kanban
Then Task 集合与 Table 一致
And 每条任务只进入一个标准状态列
And 逾期未完成任务被标记，Done 不标记逾期
AC-07 动态 Trace 统计
Given 已加载至少两个 Iteration 的 Traceability
When 改变 Project、Iteration 或搜索条件
Then 四类统计和 coverage 只基于当前范围重新计算
And coverage=round(endToEndCount/linkedDoorCount×100%)
And 选择 category 后只显示该类别记录
AC-08 精确链接与分类
Given 构造四条 DOORS 记录分别满足四类定义
When 重建 Traceability
Then 每条记录进入且只进入正确类别
And 标题相同但没有精确 ID 的记录不得建立链接
And unresolved ALM ID 显示为 Outside loaded ALM scopes
AC-09 Partial failure
Given DOORS/QC 可用但 RTC 认证失败
When 用户执行 Pull
Then 日志明确显示 RTC login failed
And 页面不得声称 ALM 已远端刷新成功
And 若返回 partial result，状态区域必须包含 ALM error
And 页面拉取前的数据不得因失败而丢失
AC-10 并发控制
Given 一个 Pull 或 Build & Pull 正在运行
When 第二个客户端再次启动任一数据操作
Then 第二个请求收到 HTTP 409
And 第一个操作继续运行并可查询进度
AC-11 分页
Given 筛选后结果超过 100 条
When 用户分别选择 25、50、100 Rows 并翻页
Then 每页条数、起止序号、总数和按钮禁用状态正确
AC-12 数据安全
Given 完成一次成功和一次失败 Pull
Then 浏览器 response、页面和日志中均不存在 Jenkins/RTC 密码、cookie 或认证 header
AC-13 Trigger Build & Pull
Given 用户已选择一个有 Jenkins Build 权限且配置完整的 Project
When 用户点击 Trigger Build & Pull 并确认
Then 前端发送一次 POST /api/tasks/build
And 后端先读取旧 Build 编号，再且仅调用一次 buildWithParameters
And 每 5 秒轮询新 Build 状态
And 新 Build 为 SUCCESS 后下载其 Artifact、刷新 ALM、重建 Tasks 和 Traceability
And 完成状态显示新 Build 编号
But 若用户取消、Build 失败或超时，则不得继续成成功 Pull，页面旧数据保持不变
AC-14 运行中取消
Given 普通 Pull 或 Build & Pull 已创建后台 job 且仍在运行
When 用户点击 Cancel & Close
Then 前端调用一次 POST /api/tasks/pull/{job_id}/cancel
And 本地 worker 停止，job 进入 Cancelled，页面原有成功数据保持不变
And 普通 Pull 不调用 Jenkins queue cancellation
And Build & Pull 只有在本次 queue item 仍处于队列中且 Project 校验一致时才取消该 item
But 已经开始执行的 Jenkins Build 不得被自动终止
AC-15 后端运行时独立性
Given 参考 GUI 项目目录不存在或旧参考路径被设置为无效值
When 用户加载 Jenkins Project 列表并完成一次普通 Pull
Then SWPM 仅使用本仓库 Python、backend/summary_backend.py 和 backend/.app_cache
And 不导入或启动参考 GUI 脚本、embedded Python 或 .app_cache
